Associação Gaia

Descrição dos comportamentos disponíveis no website e na API da Associação Gaia ao final de setembro de 2026, com separação entre funcionalidades visíveis ao usuário e recursos implementados no backend.

Versão 1.0 · Referência: 30/09/2026 · Projeto acadêmico IFSP

1. Objetivo e escopo

Este documento descreve as funcionalidades do sistema Associação Gaia considerando o estado dos repositórios até 30 de setembro de 2026. A documentação abrange o sistema como um todo, não apenas as atividades de uma pessoa da equipe.

O conteúdo foi delimitado por snapshots dos branches principais dos dois repositórios, correspondentes aos últimos merges identificados em setembro:

  • Backend: associacao-gaia-api, snapshot 520be4c498a760e2c0ab7fef011a16a3699d94b5.
  • Frontend: Site-AssociacaoGaia, snapshot 2cbc762a911a0343755cc84a473f06969b67f59b.
Critério de documentação: uma funcionalidade é descrita como integrada ao website somente quando há evidência no frontend desse fluxo. Endpoints existentes exclusivamente no backend são identificados como recursos da API, sem presumir que já possuíam uma tela conectada.
Limite temporal: recursos integrados depois de 30/09/2026 não fazem parte do escopo funcional desta versão, mesmo que estejam presentes no branch main atual.

2. Visão geral do sistema

A solução é composta por um website institucional, desenvolvido com HTML, CSS e JavaScript, e uma API REST desenvolvida em Java com Spring Boot. O backend utiliza Spring Data JPA para persistência em banco relacional e Spring Security para autenticação e autorização.

Website institucionalApresenta a Associação, seus projetos, artesãos e conteúdos de eventos. Possui navegação responsiva e páginas de cadastro e login.
Área administrativaPermite ao administrador consultar usuários, filtrar por tipo e ativar ou desativar contas.
API RESTGerencia contas, autenticação, dados de usuário, perfil de artesão e trabalhos associados ao perfil.

O website utiliza uma URL base centralizada em js/config.js. Em ambiente local, a API é apontada para http://localhost:8080; fora de localhost, o frontend utiliza o endereço hospedado no Render configurado no arquivo.

3. Papéis de usuário

TipoDescrição funcional
VISITANTETipo atribuído automaticamente a todo usuário criado pelo fluxo público de cadastro. Pode autenticar-se e utilizar as funcionalidades gerais permitidas a usuários autenticados.
ARTESAOTipo previsto para identificar usuários com perfil de artesão. A API já possui operações de consulta e atualização do próprio perfil e gerenciamento de trabalhos associados.
ADMINISTRADORTipo com permissão para listar usuários e alterar o status de contas. O frontend também restringe a exibição e o acesso à interface do painel administrativo a esse tipo.

O cadastro público não permite escolher o tipo de usuário: o backend define VISITANTE. A promoção para artesão por solicitação e aprovação administrativa não estava implementada até o marco desta documentação.

4. Site institucional

O website oferece páginas públicas organizadas por conteúdo. No snapshot de setembro, os conteúdos de eventos, agenda, projetos e catálogo de artesãos são apresentados no frontend. A presença dessas páginas não significa que seus dados sejam administrados pela API.

4.1 Página inicial

  • Apresenta a identidade e a proposta institucional da Associação Gaia.
  • Exibe seções de destaque e carrosséis de eventos e artesãos.
  • Os carrosséis da página inicial possuem navegação por controles e rotação automática implementadas em JavaScript.
  • Disponibiliza navegação para as demais áreas do website.

4.2 Eventos e agenda

  • A página de eventos apresenta cards com informações como título, local, data, imagem e categoria.
  • Há uma página de detalhe de evento preenchida a partir de identificador presente na URL e conteúdo definido no frontend.
  • A página de agenda apresenta uma composição visual de eventos salvos/destacados no próprio conteúdo do site.
  • Os links e rótulos de “Agendar” existentes no frontend não representam, neste marco, uma reserva persistida pela API.

4.3 Artesãos e projetos

  • A página de artesãos apresenta catálogo visual com informações e categorias.
  • A página individual de artesão apresenta estrutura de perfil, portfólio, contato e trajetória.
  • A página de projetos apresenta iniciativas e conteúdos institucionais.
  • Os conteúdos apresentados nessas páginas são parte da experiência de navegação do website; não se deve presumir sincronização com os endpoints de perfil e trabalhos descritos adiante.

4.4 Navegação e responsividade

  • Menu de navegação para desktop e menu lateral para dispositivos móveis.
  • Fechamento do menu móvel por botão ou sobreposição.
  • Layout desenvolvido com abordagem mobile-first e estilos responsivos.
  • Há recursos de acessibilidade no markup, como links para pular ao conteúdo principal em páginas que os incluem, rótulos e textos alternativos em elementos relevantes.

5. Cadastro de usuário

O cadastro cria uma conta na plataforma a partir do formulário disponível em pages/cadastro.html. O frontend envia os dados para a API e, após sucesso, direciona o usuário à página de login.

Dados solicitados

CampoRegra observada
NomeObrigatório; não pode estar em branco.
E-mailObrigatório e deve possuir formato válido de e-mail. É único na base.
SenhaObrigatória; armazenada no backend com codificação BCrypt.
TelefoneObrigatório no DTO de cadastro.

Fluxo de execução

  1. O usuário preenche nome, e-mail, senha e telefone.
  2. O frontend valida campos vazios e o formato básico do e-mail.
  3. O frontend envia POST /api/usuarios com os quatro campos em JSON.
  4. O backend valida o DTO, verifica se o e-mail já está cadastrado e cria a conta como VISITANTE.
  5. A senha é codificada antes da persistência; a resposta utiliza UsuarioResponseDTO, que não inclui senha.
  6. Em caso de sucesso, o frontend redireciona para login.html.

Respostas e erros relevantes

  • 201 Created: cadastro realizado.
  • 400 Bad Request: dados inválidos.
  • 409 Conflict: e-mail já cadastrado.

6. Login e gerenciamento de sessão

O login autentica o usuário por e-mail e senha. O formulário em pages/login.html envia os dados à API, que verifica as credenciais e o status ativo da conta.

Fluxo de execução

  1. O usuário informa e-mail e senha.
  2. O frontend verifica se os campos foram preenchidos.
  3. O frontend envia POST /api/usuarios/login com { email, senha }.
  4. O backend procura a conta pelo e-mail, compara a senha informada com o hash armazenado e verifica se o usuário está ativo.
  5. Se as verificações forem aprovadas, o backend gera um JWT e retorna o token junto aos dados públicos do usuário.
  6. O frontend armazena o token em localStorage na chave gaia_token e os dados do usuário em gaia_usuario.
  7. O usuário é redirecionado para a página inicial.

Regras e respostas

  • 200 OK: autenticação realizada; resposta contém token e usuário.
  • 400 Bad Request: falha de validação dos dados.
  • 401 Unauthorized: e-mail ou senha inválidos.
  • Conta inativa: login recusado pelo backend com exceção específica de usuário inativo.

Nas requisições protegidas, o frontend envia o token no cabeçalho Authorization: Bearer <token>. A API não mantém sessão HTTP no servidor; o controle é stateless.

7. Consulta e edição de dados do usuário

A API disponibiliza operações para consultar dados de usuário e atualizar informações da própria conta. A resposta pública não contém senha.

Consulta

  • Consulta por identificador: GET /api/usuarios/{id}.
  • Consulta por e-mail: GET /api/usuarios/email/{email}.
  • O acesso é permitido ao próprio usuário correspondente ou ao administrador.

Atualização

PUT /api/usuarios/{id} permite atualizar nome e telefone. A senha também pode ser atualizada quando enviada preenchida no DTO. A operação é permitida ao próprio usuário ou ao administrador.

O e-mail e o tipo de usuário não são alterados por esse fluxo de atualização implementado no service observado.

8. Painel administrativo — gerenciamento de usuários

O painel administrativo está disponível em pages/painel-administrativo.html e utiliza js/admin.js. A interface é exibida somente quando existe sessão local e o usuário armazenado possui o tipo ADMINISTRADOR.

Funcionalidades disponíveis

  • Consultar a lista de usuários cadastrados.
  • Exibir nome, e-mail, tipo de usuário, data de cadastro e status da conta.
  • Filtrar os registros por tipo de usuário na interface.
  • Exibir contador de usuários e estado de lista vazia.
  • Ativar ou desativar uma conta por meio de ação individual.

Fluxo de listagem

  1. O script verifica a existência do token e dos dados do usuário em localStorage.
  2. Se não houver sessão ou o tipo não for ADMINISTRADOR, o usuário é redirecionado para fora do painel.
  3. O painel envia GET /api/usuarios com o token JWT.
  4. O backend autoriza a listagem apenas para administradores e retorna os usuários.
  5. O frontend aplica o filtro selecionado e renderiza a tabela.

Ativação e desativação

  1. O administrador aciona “Ativar” ou “Desativar” na linha do usuário.
  2. O frontend inverte o valor atual de ativo e envia PATCH /api/usuarios/{id}/status.
  3. O corpo da requisição contém o novo valor booleano: { "ativo": true } ou { "ativo": false }.
  4. O backend verifica a permissão administrativa, atualiza o status e persiste a alteração.
  5. O frontend recarrega a listagem para refletir o novo estado.
Importante: a checagem de papel no frontend controla a experiência visual, mas não substitui a autorização do backend. As rotas administrativas também são protegidas no Spring Security.

9. Perfil do artesão — recurso disponível na API

No snapshot do backend em 30/09, já existiam ArtesaoController e ArtesaoService. Eles permitem consultar e atualizar o perfil associado ao usuário autenticado. O identificador do usuário é obtido do principal autenticado, não enviado pelo cliente.

MétodoEndpointComportamento
GET/api/artesaos/meRetorna o perfil de artesão vinculado ao usuário autenticado.
PUT/api/artesaos/meAtualiza os dados do perfil vinculado ao usuário autenticado.

Os campos tratados pelo service incluem nome de exibição, título curto, biografia, texto de apresentação, cidade, data de entrada como membro, locais de atendimento, avatar e links de Instagram, WhatsApp e Facebook.

Se não houver perfil de artesão associado ao usuário, o service lança exceção específica de artesão não encontrado.

Limite de integração: embora os endpoints existissem no backend, o snapshot do frontend não comprova um fluxo de edição de perfil conectado a essas rotas. Por isso, esta seção documenta a capacidade da API, não uma funcionalidade pública integrada do website.

10. Trabalhos — recurso disponível na API

O backend também possuía operações para cadastrar, listar, atualizar e excluir trabalhos associados ao perfil do artesão autenticado.

MétodoEndpointComportamento
POST/api/trabalhosCadastra um trabalho no portfólio do artesão autenticado.
GET/api/trabalhos/meusLista os trabalhos do artesão autenticado, do mais recente para o mais antigo.
PUT/api/trabalhos/{id}Atualiza um trabalho, desde que pertença ao artesão autenticado.
DELETE/api/trabalhos/{id}Exclui um trabalho, desde que pertença ao artesão autenticado.

Dados de um trabalho

CampoRegra
imagemUrlObrigatório; URL da imagem, máximo de 255 caracteres.
legendaObrigatória; máximo de 150 caracteres.
descricaoOpcional.
categoriaOpcional; máximo de 100 caracteres.

O backend determina o artesão a partir do usuário autenticado e preenche a data de publicação automaticamente. Nas operações de atualização e exclusão, o service verifica a propriedade do trabalho. Uma tentativa de alterar trabalho pertencente a outro artesão resulta em acesso negado.

Limite de integração: a existência do CRUD na API não comprova que o website, no snapshot de setembro, oferecia telas conectadas para gerenciar o portfólio. O catálogo público observado era conteúdo do frontend.

11. Segurança e regras transversais

Autenticação

  • Autenticação por JWT.
  • Token enviado em requisições protegidas pelo cabeçalho Authorization: Bearer.
  • Política de sessão stateless.
  • Senhas armazenadas com BCrypt.

Autorização observada no snapshot de setembro

  • Cadastro e login são públicos.
  • Listagem geral de usuários é restrita a ADMINISTRADOR.
  • Consulta e atualização de usuário por identificador/e-mail são limitadas ao próprio usuário ou administrador, conforme as expressões @PreAuthorize.
  • Alteração do status de usuário exige ADMINISTRADOR.
  • As demais rotas exigem autenticação, salvo as explicitamente liberadas.
Observação de implementação: no snapshot histórico consultado, ArtesaoController e TrabalhoController não possuíam anotações de autorização por papel em seus métodos. As rotas exigiam usuário autenticado pela regra geral, e a lógica de trabalhos verificava a propriedade nas operações de atualização e exclusão. Não se deve documentar uma restrição a papel ARTESAO nesses endpoints como se ela já estivesse configurada naquele marco.

Tratamento de falhas

  • 400 Bad Request: falha de validação dos dados recebidos.
  • 401 Unauthorized: ausência ou invalidade de autenticação, ou credenciais inválidas no login.
  • 403 Forbidden: usuário autenticado sem autorização para a operação ou tentativa de alterar trabalho de outro artesão.
  • 404 Not Found: recurso ou perfil associado não encontrado.
  • 409 Conflict: e-mail já cadastrado.
